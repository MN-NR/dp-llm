# LS04 Multi-GPU DP Training — Experiment Log

Chronological record of what was done, what was found, and why. Kept so that
future runs and readers don't have to re-derive this from scratch, and so
that pre-fix and post-fix checkpoints are never treated as if they came from
the same pipeline.

**Environment**: conda env `dp-llm` on LS04 (2x L40S, GPUs 0+1 only).
`torch==2.5.1+cu121`, `opacus==1.5.4`, `peft==0.18.1`,
`transformers==4.57.6` (see Bug 1 — this was downgraded from `5.5.4`
mid-session; anything trained before that downgrade is invalid, see below).

---

## Goal

Test whether a larger global/effective DP batch size improves downstream
utility for VaultGemma DP-LoRA fine-tuning (ε=5.0, LR=2e-5, 8 epochs),
using both GPUs on LS04 for one synchronized DP-DDP run rather than two
independent single-GPU jobs. Baseline for comparison: an existing
RTX 5090 sweep at global batch 64.

## Multi-GPU DP infrastructure

`finetune/train_dp.py` is single-GPU only (Opacus doesn't support plain
multi-GPU). `finetune/train_dp_ddp.py` already existed in the repo,
purpose-built for LS04's 2x L40S using Opacus's
`DifferentiallyPrivateDistributedDataParallel` (DPDDP), but had never been
run to completion. Verified correct by reading the installed Opacus source
directly (not just trusting the docstring):

- `DistributedUniformWithReplacementSampler` shards the dataset into
  **disjoint** per-rank chunks — no duplicate-dataset training across ranks.
- Noise is added **once** (rank 0 only); gradients are combined via
  `all_reduce` (sum, then divide by world_size for mean reduction) —
  equivalent to single-machine DP-SGD on the full global batch.
- `get_noise_multiplier()` is calibrated against
  `sample_rate = 1/len(original_dataloader)`, where that loader is built
  with `batch_size = global logical batch` — i.e. calibration uses the true
  **global** batch, not a per-GPU halved value.

Changes made to `finetune/train_dp_ddp.py`:
- Added `--learning-rate` and `--epochs` CLI overrides (previously only
  settable by editing `config.py`'s shared MODELS registry).
- Fixed a checkpoint-collision bug: the original `run_tag` only encoded
  epsilon+seed, so a batch-256 run would have silently overwritten a
  batch-128 checkpoint at the same epsilon. Batch size is now part of the
  tag.

Dataset: `instruction_recall_dataset/dataset/processed/` didn't exist in
this (fresh-cloned) checkout — gitignored, generated by
`instruction_recall_dataset/build_instruction_dataset.py`. Rebuilt
deterministically (seed=42, unchanged builder) from the same cached AG
News / MNLI / AI4Privacy HF datasets already present in
`~/.cache/huggingface`, at the path historical single-GPU runs used
(confirmed via `~/.bash_history`).

## Bug 1: `transformers==5.5.4` broke VaultGemma tokenization

First batch-128 run (8 epochs) completed in ~9h with a suspicious
`val_loss ≈ 0.0001` at epoch 1. Root cause: `transformers==5.5.4` shipped a
rewritten `GemmaTokenizer` that only loads from `tokenizer.json` (fast
format). VaultGemma's HF repo only ever published the legacy
`tokenizer.model` (SentencePiece) — confirmed by querying the HF Hub API
directly. When `tokenizer.json` is absent, the class **silently** falls
back to a 5-token stub vocab (`pad/eos/bos/unk/mask` only) instead of
raising an error. Verified concretely: raw `sentencepiece` on the same
`tokenizer.model` file tokenizes correctly; `GemmaTokenizer.from_pretrained`
under `transformers==5.5.4` turned "Hello world..." into `[<bos>, <unk>]`.

This affected **every Gemma-family model** in `config.py` (`vault_gemma`,
`gemma_2b_it`, `gemma3_1b` — all route through
`if "gemma" in model_name_lower`), via `train_dp.py` and `train_dp_ddp.py`
identically. Not multi-GPU-specific, not something introduced this
session — a pre-existing environment problem waiting to be hit.

**Fix**: downgraded to `transformers==4.57.6` (newest 4.x release, above
VaultGemma's own `transformers_version: 4.53.2` requirement in
`config.json`; confirmed via wheel inspection that 4.53.2/4.55.0/4.57.6 all
still use the SentencePiece-based tokenizer, and the break happened at the
5.0.0 major bump). Verified `peft==0.18.1` has no version floor on
`transformers` that this violates. Re-verified real tokenization,
label masking, and model loading (`VaultGemmaForCausalLM`) after the
downgrade.

**Discarded** (produced under the broken tokenizer, invalid — deleted from
`checkpoints/` and `results/`): the first batch-128 pilot and first
batch-128 full 8-epoch run.

## PII metric investigation: strict vs. relaxed F1

`evaluate_pii_detection` (`evaluation/eval_metrics.py`, "strict") splits on
`;` and deduplicates via `set()` before exact-match scoring.
`relaxed_pii_scores` (`finetune/test_model.py`, "relaxed") splits on `;`
**or newline**, does **not** deduplicate (list, not set), and matches on
≥50% token overlap. Strict F1 (0.538/0.513 for 128/256) coming out *higher*
than relaxed F1 (0.259/0.245) is counterintuitive — traced to relaxed's
lack of deduplication: repeated predicted items count as extra false
positives there but are invisible to strict's set-based dedup.

Added (new, not previously in the repo) a diagnostic
"unique F1" — same loose overlap-matching as relaxed, but predicted/gold
items deduplicated first, isolating the repetition confound from the
matching-strictness question. Confirmed: once duplicates are removed,
loose matching outperforms strict (0.596/0.571 vs 0.538/0.513), i.e. the
matching criterion itself was never the issue — duplicate predictions were.

## Repetition root-cause investigation (no training/generation changes)

Ran, per explicit instruction: no `repetition_penalty`, no
`no_repeat_ngram_size`, no custom stopping, no `max_new_tokens` change —
investigation only.

1. **Does the training target contain EOS?** No.
   `canarybench/prompt_format.py:build_supervised_text`'s non-chat-template
   fallback built `full_text = prompt + "\n\n### Response:\n" + target`
   with no EOS appended anywhere, and `tokenizer.add_eos_token = False`, so
   the tokenizer didn't add one either. Verified empirically: EOS token id
   never appeared in a real training example's tokenized `full_text`.
2. **Is EOS masked out of labels, or just never there?** Never there — not
   a masking bug. Nothing to unmask; the token simply doesn't exist in the
   sequence to begin with.
3. **Are `eos_token_id`/`pad_token_id` correct at generation time?** Yes.
   Train-time (`GemmaTokenizer`) and eval-time (`GemmaTokenizerFast`, via
   `AutoTokenizer(use_fast=True)`) report identical IDs
   (`bos=2, eos=1, pad=0`), and `test_model.py` passes them correctly into
   `model.generate()`. Not an ID-mismatch bug.
4. **Same termination formatting at train vs eval?** Functionally yes.
   `test_model.py` has its own local `build_prompt()` (doesn't import the
   canonical `canarybench.prompt_format` module as that module's own
   docstring says call sites should) but produces a byte-for-byte identical
   string to training's `prompt_only` for the current no-chat-template
   case. Latent drift risk if a chat template is ever added to one path and
   not the other — not fixed here, out of scope for this task.
5. **Does the model ever generate EOS naturally?** Checked on 50 fixed val
   `pii_detection` examples, generation config completely unmodified:
   **0/50** for batch-128, **0/50** for batch-256.
6. **Is this DP-specific?** No. Found a pre-existing non-DP VaultGemma
   baseline checkpoint at
   `/home/noora/Downloads/dp-llm/dp-llm/checkpoints/vault_gemma/baseline/final`
   (older clone on this machine, matching LoRA config modulo the
   DP-forced `lora_dropout=0.0` vs its `0.05`). Also **0/50** natural EOS.
   Repetition was already severe there (repetition_fraction 0.642, mean
   duplicate count 6.77, unique F1 0.658) — DP training measurably
   *amplifies* it (repetition_fraction 0.674-0.676, mean duplicate count
   8.06-8.57, unique F1 0.571-0.596) but does not cause it.

**Conclusion**: the target's tokenized form never contained an EOS token
for *any* checkpoint in this repo's history (DP or non-DP) — a
pipeline-level bug in the shared prompt-formatting code, not something
specific to DP-DDP or to this session's multi-GPU work.

## Bug 2 (fix): EOS was missing from the supervised training target

**Root cause**, precisely: `build_supervised_text`'s fallback branch
returned `full_text = f"{prompt_only}{target}"` with nothing after
`target`, and `GemmaTokenizer`'s `add_eos_token=False` meant tokenization
didn't add one either.

**Fix** (`canarybench/prompt_format.py`, `build_supervised_text`): the
fallback (non-chat-template) and lm/empty-prompt branches now append
`tokenizer.eos_token` after `target`, so `full_text` ends with the target
immediately followed by EOS. The chat-template branch is intentionally
**not** touched — chat templates typically already emit their own
turn-termination token when `add_generation_prompt=False`, so blindly
appending EOS there risked double-EOS for any model that does use a chat
template (none of the models run this session do, but the function is
shared code — see the module's own docstring about not letting call sites
drift).

**Verified** end-to-end through the real training path
(`MultiTaskDataset.__getitem__`): `full_text` now ends in `<eos>`, the
tokenized `input_ids` contain `eos_token_id` at the expected final content
position, and — the critical check — that position is **not** masked to
`-100` in `labels`, i.e. it is a genuine loss-bearing target the model will
be trained to predict.

Side effect: a handful of records that were exactly at the 128-token cap
now exceed it by one token (the added EOS) and get filtered by
`MultiTaskDataset`'s length check. Train: 81,456 → 81,375 (-0.1%). Val:
2,938 → 2,935 (-0.1%). Negligible; sample rate for DP accounting recomputed
accordingly (128/81,375 ≈ 0.0015730 vs previous 0.0015422 — noise
multiplier essentially unchanged, 0.5521 → 0.5521 at epochs=8).

### Old (no EOS) vs. new (EOS-fixed) batch-128 — final comparison

Same protocol as the repetition investigation above (50 fixed val examples
for EOS rate; full 984 `pii_detection` val examples, `--save_all_samples`,
for repetition/unique-F1 stats).

| Metric | OLD (no EOS) | NEW (EOS-fixed) |
|---|---|---|
| EOS generation rate (50 fixed examples) | 0/50 | **50/50** |
| Repetition fraction | 0.674 | **0.023** (29x reduction) |
| Mean duplicate count | 8.06 | **0.04** |
| Unique F1 | 0.596 | **0.802** |
| Unique precision | 0.441 | **0.841** |
| Unique recall | 0.917 | 0.767 (trade-off, see below) |
| PII exact match | 0.109 | **0.483** |
| Best validation loss | 0.2926 | **0.2655** |
| Classification / NLI accuracy | 23.9% / 33.5% | 23.8% / 33.4% (unchanged — loss-based eval, not generation-dependent) |
| Member/reference memorization gap | 0.0139 | 0.0193 (small increase, both negligible) |

**Conclusion**: the missing-EOS bug was a substantial, previously-hidden
confound on every earlier batch-size comparison in this log. With it
fixed: repetition drops ~29x, unique F1/precision/exact-match improve
sharply, and validation loss improves too. The one trade-off is unique
recall (0.917→0.767) — the old model's uncontrolled repetition was
effectively spraying many candidate values per example and occasionally
catching the right one by volume, not understanding; the fixed model is
more conservative but far more precise. Net effect across precision, F1,
exact match, and val loss is an unambiguous improvement, not a wash.

**Implication for earlier batch-64/128/256 comparisons in this log**: they
were all run without the EOS fix, so their PII-related numbers in
particular should be read as "how these batch sizes compare to each other
under the same bug," not as final results. The batch-size finding itself
(256 ≈ 128, no improvement) is likely still directionally valid since the
bug affected both equally, but has not been re-verified under the fixed
pipeline.

`finetune/train_baseline.py` shares `dataset.py`/`MultiTaskDataset` with
the DP scripts, so it picks up the EOS fix automatically — no additional
code changes needed there. Added `--batch-size`/`--grad-accum`/

## Known inefficiency: `dp_physical_batch_size=2` (not fixed yet, deliberately)

All DP runs this session (batch-128/256 pre-EOS-fix, and all three
EOS-fixed epoch-horizon runs) used `dp_physical_batch_size=2`, inherited
unchanged from `finetune/config.py`'s pre-existing `vault_gemma` entry —
not something chosen or changed this session. Peak GPU memory actually
used across every one of these runs: **4.05 GB of 46.07 GB available per
L40S (8.8% utilization, 91.2% headroom unused)**.

This does **not** affect correctness: Opacus's `BatchMemoryManager` splits
a Poisson-sampled logical batch into physical microbatches purely for
memory management — it accumulates summed clipped per-example gradients
across all microbatches and adds noise once on the last one before
stepping, so the final noised gradient, the sample rate, the noise
multiplier, and ε are all completely independent of the physical batch
size used to process the same logical batch. It only affects wall-clock
speed (more, smaller kernel launches = more fixed per-step Python/CUDA
overhead relative to actual compute) and memory footprint.

Given the confirmed ~9x memory headroom, this is very likely a major
contributor to why these DP runs have taken 9-30+ hours rather than a
fraction of that. **Decision** (user, this session): do not interrupt the
in-flight epochs=16 run to fix this — it was already past epoch 9/16 with
strong results, and restarting would discard real sunk progress for an
uncertain net time savings. Use a substantially larger
`dp_physical_batch_size` (e.g. 16-32, still well within the 46GB budget)
for any DP run launched after epochs=16 completes.

## AG News/MNLI evaluator repair (investigation, epochs=12 checkpoint)

User flagged that the production classification/NLI evaluator
(`evaluation/loss_based_eval.py`'s `_avg_label_loss`, argmin raw
conditional-label loss) shows severe label-string priors (AG News
collapses to Sci/Tech, MNLI disfavors neutral) and must not be used for
paper utility numbers as-is. Evaluation only -- no training changes.

Built `evaluation/classification_eval_methods.py` (raw reused unmodified
from `loss_based_eval.py`; new calibrated/PMI method with null prompts
built from the exact literal instruction strings
`instruction_recall_dataset/build_instruction_dataset.py` uses, content
field left empty; new generation method reusing `_build_prompt` so all
three methods share identical prompt construction) and
`evaluation/run_classification_eval.py` (driver, fixed stratified sample
by default, >=20 examples/class).

**Zero-shot base**: generation invalid-rate 100% -- inspected raw text,
confirmed genuine (an untuned base model free-writes plausible article
continuations instead of emitting a label; not a parsing bug).

**Epochs=12 EOS-fixed, AG News**: generation 81.25% (invalid=0%, all 4
labels, balanced) vs. raw-loss 23.75% (collapsed Sci/Tech 76/80) vs.
calibrated 30.0% (collapsed World/Business only) -- a 51-point disagreement
between calibrated and generation, triggering the user's explicit "stop
and investigate" rule. MNLI: all three methods within ~3 points of each
other, near chance -- no investigation needed there, likely a genuine
difficulty rather than a measurement artifact.

**Root cause, confirmed with a controlled test**: `_avg_label_loss`
tokenizes with `add_special_tokens=False` (no BOS), but
`finetune/dataset.py`'s actual training input uses the tokenizer's default
(`add_special_tokens=True`, BOS included). Direct A/B test, same model,
same input, only BOS differing: NLL for the correct label "Business" is
14.44 without BOS (probability ~5e-7, nonsense) vs. 1.125 with BOS (normal,
confident). Every loss-based prediction has been scored in an
out-of-distribution regime the model was never trained on.

Added a new "constrained/joint" method (scores the complete trained
response -- label tokens + EOS -- via **sum** NLL, not average, so it
can't be diluted by cheap deterministic follow-up tokens the way averaging
can) for comparison. Audited `_avg_label_loss` per the user's checklist:
scores label tokens only (not EOS); uses average NLL, not sum; prompt/full
tokenization boundary is clean (verified, not a bug); whitespace at the
prompt/label boundary is correct (matches training); response prefix
matches training. Label token counts vary sharply (World/Sports/Business=1
token, Sci/Tech=3; neutral=1, contradiction=2, entailment=3) -- a real
secondary risk from averaging, independent of the BOS bug.

**After the BOS fix** (reimplemented locally for the comparison only, not
yet applied to `loss_based_eval.py`), same 80-example AG News sample:

| Method | Broken | BOS-fixed | Agreement w/ generation (BOS-fixed) |
|---|---|---|---|
| Raw-loss | 23.75% | 85.0%, all 4 labels, balanced | 96.25% |
| Calibrated/PMI | 30.0% | 61.25%, still favors World (39/80) | 61.25% (still disagrees) |
| Constrained/joint (sum NLL, label+EOS) | 27.5% (collapsed Sports) | **82.5%**, all 4 labels, balanced | **98.75%** |
| Free generation | 81.25% (unaffected by the bug) | -- | -- |

Constrained generation vs. free generation: not implemented as a separate
`LogitsProcessor` decoder -- for a closed 3-4-way candidate set,
exhaustively scoring every candidate's full-sequence likelihood (the
constrained/joint method) is mathematically exact constrained decoding, no
approximate search over the same candidates could do better. The near-
identity result (98.75% agreement) confirms free generation already
behaves as if constrained.

Leakage check corrected mid-investigation: first pass flagged 80/80
examples as "leaking" the gold label into the prompt, which was a false
alarm from checking the full input including the instruction line (which
lists all 4 category names for every example, by design). Restricted to
the article-text portion only: 3/80 (3.75%) incidental overlaps (e.g. wire
service name "Sports Network", ordinary usage "World cocoa prices") -- not
a systematic leak.

**Status as of this log entry**: root cause found and confirmed for AG
News/epochs=12. `_avg_label_loss` and the production evaluator have **not**
been modified. MNLI-specific BOS-fix verification, and extending this
audit to the other checkpoints (zero-shot, 16, 20), have not been run yet
-- awaiting user direction on how to proceed.
